# Codify 우수성 개선 평가 v1

> 보존 상태: 2026-10-14 사용자 요청으로 원본 실행 로그·임시 실행 코드·보존 압축본을 삭제했다. 이 문서의 과거 경로·해시는 당시 기록이며, 현재 보존 자료는 README와 최종 보존 기록을 기준으로 확인한다.

상태: 개발 후보와 사례 준비 중. 확인 평가를 고정하거나 시작하지 않았다.

## 목적과 완료 조건

기존 평가 완료와 별개의 목표다. gpt-6.1-sol / medium에서 Codify가 실제 코드 품질, 보안, 질문 판단, 총 비용, 완료 시간, orchestration을 개선하는지 확인한다. 기존 완료 기록과 C0 결과는 변경하지 않는다. 스킬 분량 감소, 정적 리뷰 통과, 소수 pilot 통과만으로 우수성을 선언하지 않는다.

요구1: 코드 품질은 공개 행동, 영향받는 회귀, 복구 경로와 범위 보존으로 측정한다. 요구2: 보안은 해당 과제에 명시된 권한·입력·저장·오류 노출 경계의 반례를 실제 실행한다. 요구3: 질문은 중요한 선택의 해결률과 불필요·중복 질문을 함께 측정한다. 요구4: 비용은 root, worker, 리뷰, 통합, 실패와 재시도를 포함한다. 요구5: 속도는 시작부터 통합·검증 완료까지의 시간이다. 요구6: 위임은 독립적인 작업의 결과가 실제 의사결정에 쓰였는지와 총 비용·시간 기여를 측정한다. 요구7: 평가 전용 Docker 컨테이너는 작업 종료 후 제거하고, 필요한 결과와 원본은 호스트에 보존한다. 사용 중인 고정 이미지는 마지막 실행·채점 후 정리한다. 다른 프로젝트 리소스는 보존한다.

## 조건과 데이터 분리

A: 스킬 없음. C0: 기존 동결 후보. C1: 새 개발 후보. 모델과 reasoning은 모두 동일하게 고정한다. 각 실행은 새 컨텍스트이고 다른 결과·개선 이유·정답·oracle을 제공하지 않는다.

D01/D02 등 개발 사례는 후보 조정과 실행기 검증에만 사용한다. 기존 E/S/W/H는 공개된 회귀 자료이며 새 확인용 holdout이라고 부르지 않는다. 독립 설계자가 C1이나 기존 실패를 읽지 않고 신규 Q 사례를 작성한다. root는 C1 고정 전 Q 구현·정답을 읽지 않는다. 사례 작성 자체는 봉인이 아니다. 공개 요구사항과 oracle 대응, 시작 실패, 올바른 기준 구현 성공, 중요 동작 제거 시 실패를 별도 검증한 뒤 사례와 후보·채점기·환경 hash를 고정한다.

확인 사례는 난이도 pilot용과 최종 확인용으로 나눈다. pilot을 보고 후보를 수정하면 사용된 사례는 개발용으로 이동한다. 확인 사례나 판정을 본 뒤 후보가 바뀌면 새 확인 자료를 준비한다. 쉬운 사례만 선택하거나 실패한 반복을 제외하지 않는다.

## 지표와 판정

품질: 요구사항별 행동 통과, 전체 과제 완료, 보호 경계·회귀, 결함 심각도. 보안: 악용 반례 통과 및 중대한 위반. 질문: 필요한 미결정 사항을 해결한 비율, 불필요 질문, 중복 승인, 질문 없이 임의 결정한 중요 사항. 비용: 실제 native 사용량의 입력·캐시 입력·출력 토큰을 분리하고 모든 참여 세션을 합산한다. 청구 금액을 관측하지 못하면 토큰 비용 지표라고 명시하며 금액 절약으로 표현하지 않는다. 시간: wall clock, root 작업 시간, worker 시간, 대기·통합·복구·채점 시간 별도. 외부 평가 비용은 제품 실행 비용과 분리하되 총 연구 비용도 공개한다.

분석은 모든 할당 실행을 포함한다. 성공 실행만 골라 비용을 비교하지 않는다. 실패·timeout·규칙 위반의 비용도 포함하고 성공당 총 비용을 추가 보고한다. 실제 환경 장애를 제외한 실패는 재실행하지 않는다. 인프라 재시도는 사전 규칙과 최대 횟수에 따라 원본과 새 실행을 함께 기록한다.

최종 확인은 과제 단위 대응 비교와 95% 불확실성 구간을 사용한다. 사용자 최신 지시(2026-10-14)에 따라 토큰 사용량은 합격·완료 조건에서 제외하고 참고 지표로만 측정·보고한다. 증가 허용 한계나 절감 목표로 후보를 탈락시키지 않는다. 실제 원본 사용량, 실패 비용과 관측 가능한 불확실성은 계속 공개하며, 사용량만으로 전체 우수성을 판단하지 않는다. 시간 우위의 사전 목표는 15% 이상 감소이며, 구간 상한이 개선 없음의 경계 1 아래여야 한다. 품질·보안·필요한 결정 해결률은 악화되지 않는 근거가 동시에 필요하다. 품질 및 보안 우위는 각각의 실제 행동 결과 차이로 별도 입증한다. 하나의 지표가 좋아졌다고 전체 우수성으로 합치지 않는다. 표본 수와 비열등 한계는 난이도 pilot 이후, 확인 실행 전에 근거와 함께 고정한다. 그 전 결과는 탐색 결과다.

## 실행 단계와 검증

단계1: C0 및 설치본 보존. C1에서 탐색 종료, 필요한 질문 확인, 실패 원인 분류, 위험별 검증, 위임의 실제 기여를 보완하고 독립 정적 리뷰한다.
단계2: D 사례 시작/gold/negative를 검증한다. A/C0/C1을 동일 환경에서 실행하여 관측한 행동·비용과 결함을 근거로 후보를 수정한다. 반복 수·순서·실행 제한은 비교 전에 고정한다.
단계3: 신규 독립 확인 사례를 충분히 마련하고 공개 계약 대응 및 oracle 변별력을 검증한다. 별도 baseline 난이도 pilot으로 천장 효과와 실행 시간을 확인한다. 품질 차이를 검출할 수 없는 자료라면 확인 평가를 시작하지 않는다.
단계4: 변경하지 않는 최종 C1과 확인 cohort를 고정한다. 순서를 사전 무작위화하고 사례별 반복을 대응시킨다. 위임 비허용 단독 실행 비교와 위임 허용 orchestration 비교는 별도 cohort로 보고한다. 후자에서는 모든 조건에 같은 런타임·권한·인원 상한을 제공하며 worker 비용을 합산한다.
단계5: 가린 조건의 독립 리뷰와 실제 행동 채점, 전체 실행·실패·질문·비용 보고. 각 요구의 우수성이 확인돼야 목표를 완료한다. 근거가 부족하면 부족한 차원을 남겨두고 개발을 이어간다. 수정된 후보는 새 버전과 새 확인 cohort가 필요하다.

Docker: 이름만으로 소유권을 추정하지 않고 mount와 실행 metadata를 대조한다. 호스트 mount 결과를 보존하고 writable layer의 앱 자료·진단 파일은 삭제 전 압축 보존한다. SDK, analyzer, shader, telemetry 캐시는 재생성 가능한 자료로 구분한다. 전체 system prune은 사용하지 않는다. 여유 공간 최소 3GiB, 초기 동시 실행 1개. 컨테이너가 살아있다는 것만으로 모델 실행 중이라고 추정하지 않고 실제 프로세스를 확인한다.

현재 미완료: 새 사례 qualification, 행동 pilot, 확인 표본 수 및 경계 고정, orchestration 계측/실행, 실제 우수성 입증, 최종 설치본 승격 및 사용 이미지 정리.

## 사용자 승인 축소안 (2026-10-14)

사용자는 대표 평가로 축소하는 안을 선택했다. 이번 완료 범위는 코딩 3개(입력·권한 경계, 저장·재시도·실패 보존, 비동기·동시 실행·취소), 질문 2개(필요한 선택 질문, 불필요한 질문 없이 완료), 작업 분담 1개다. A·C0·C24의 실제 행동 결과를 비교하고 주장 범위를 관측한 대표 사례로 제한한다. 기존 나머지 18개 조건, 큰 표본의 통계적 우수성 입증과 범용 세션 인증·재개·작업자 추적 실행기 확장은 이번 완료 조건에서 제외한다. 앞의 전체 평가·통계 판정 요구와 충돌하면 이 최신 사용자 승인 범위를 적용한다. 품질·소프트웨어 보안·복구·질문·분담 결과, 실제 시간과 토큰 측정, 실패 기록 보존과 Docker 정리는 유지한다. 토큰은 참고 지표다.
