# 개선된 Codify 사용 사례

[README](../README.md) · [평가·개선 과정 보고서](evaluation-improvement-report.md)

Codify가 특히 잘 맞는 작업은 **변경할 행동과 완료 기준을 설명할 수 있고, 정상 경로와 실패 경로를 함께 확인해야 하는 코드 작업**이다. 현재 코드를 먼저 확인하고, 결과를 바꾸는 미결정 사항만 질문한 뒤, 담당 에이전트가 구현·통합·검증을 마무리하도록 요청한다.

아래 예시는 C24 지침에 근거한 활용 제안이다. 예시 자체를 새로 실행·평가한 것은 아니다. 최종 대표 평가는 Python 표준 라이브러리 과제이며 다른 언어·제품·운영 환경의 우위를 보장하지 않는다. 예시의 시작 경로는 실제 저장소 경로로 바꾼다.

## 요청에 포함하면 좋은 내용

| 입력 | 설명 |
|---|---|
| 목적 | 사용자가 겪는 문제와 바뀌어야 하는 행동 |
| 시작 경로 | 알려진 구현·호출부·관련 테스트의 위치 |
| 범위 | 변경 가능한 파일·기능과 보존할 기존 변경 |
| 완료 조건 | 정상·실패·복구 상황에서 기대하는 관측 결과 |
| 기존 결정 | 이미 정한 정책과 승인. 다시 묻지 않도록 제공 |

자료가 부족하면 필요한 부분만 추가로 확인하면 된다. 매번 긴 명세서를 만드는 절차는 아니다.

### 내 작업에 맞춰 쓰는 공통 템플릿

대괄호 항목을 실제 작업에 맞게 채운다. 이미 정한 정책은 그대로 전달하고, 미결정 사항이 없다면 해당 줄은 생략한다.

```text
$codify
목적: [사용자가 겪는 문제와 바뀌어야 하는 행동]
시작 경로: [관련 구현·호출부·테스트 경로]
변경 범위: [변경할 기능 또는 파일]. 기존 사용자 변경은 보존해줘.
기존 결정: [이미 정한 동작·정책·승인]
미결정 사항: [결과를 바꾸는 선택이 있다면 구현 전에 질문]
완료 조건: [정상·실패·복구 상황에서 확인할 행동]
구현과 관련 검증을 끝내고, 변경 내용·실제 검사 결과·남은 한계를 보고해줘.
```

빠른 시작용 사례별 프롬프트는 [README](../README.md#복사해서-쓰는-샘플-프롬프트)에 있고, 아래에는 각 사례의 상황과 확인할 결과를 함께 정리했다.

## 사용1: 재현 가능한 버그와 회귀 수정

**적합한 상황:** 빈 목록·경계값·잘못된 입력·상태 공유에서 문제가 재현되고, 영향받는 동작이 구체적이다.

```text
$codify
검색 결과가 빈 목록일 때 상세 화면 이동에서 예외가 발생한다.
시작 경로는 검색 결과 화면, 이동 함수, 관련 테스트다.
빈 목록에서는 이동하지 않고, 단일·복수 결과의 기존 이동은 유지해줘.
재현 경로와 영향받는 회귀를 검사하고 실제 결과를 보고해줘.
```

**확인할 결과:** 원인과 실제 변경의 연결, 재현 조건 해결, 관련 회귀 통과, 범위 밖 변경 여부. 스킬은 알려진 경로에서 탐색을 시작하고 해결·검증에 필요한 범위를 파악하면 탐색을 멈추도록 안내한다.

## 사용2: 외부 입력·권한·파일 경로가 얽힌 기능

**적합한 상황:** 문서 내보내기, 파일 업로드, 외부 응답 저장처럼 검증과 권한 판단이 부수효과보다 먼저 일어나야 한다.

```text
$codify
문서 내보내기 기능을 구현해줘.
기존 권한 정책을 사용하고, 권한이 없으면 조회·저장·감사 기록을 남기지 않아야 한다.
파일 경로가 허용 디렉터리를 벗어나지 않게 해줘.
외부 렌더러가 성공을 반환해도 결과 형식이 유효한지 저장 전에 확인해줘.
정상 출력과 권한 거부·잘못된 경로·잘못된 렌더러 출력을 검증해줘.
```

**확인할 결과:** 효과 발생 전 권한·형식 검사, 안전한 오류, 저장 결과와 반환 정보의 일치. R1에서 이런 경계를 검사했지만 운영 서비스 전체의 보안 감사까지 검증한 것은 아니다.

## 사용3: 영속 저장·중복 처리·재시도·복구

**적합한 상황:** 주문·작업 큐·동기화 상태가 재시작 뒤에도 유지돼야 하고, 같은 요청을 다시 보내도 중복 효과가 생기면 안 된다.

```text
$codify
작업 큐 저장과 재시도를 구현해줘.
같은 사용자와 요청 키는 동일 작업으로 처리하고, 다른 사용자의 키는 분리한다.
재시작 후 미완료 작업을 복원하고, 저장 실패 시 기존 상태를 보존해줘.
실제 파일 또는 DB를 사용해 중복 요청·재시작·저장 실패·복구 후 재시도를 확인해줘.
```

**확인할 결과:** 실제 영속 저장과 새 인스턴스 복원, 실패 시 데이터 보존, 중복·동시 처리 규칙. 같은 메모리 객체를 다시 사용하는 검사만으로 재시작 복원을 인정하지 않는다. 최종 R2는 실제 SQLite 동작을 다뤘다.

## 사용4: 비동기 경합·취소·종료 처리

**적합한 상황:** 같은 요청을 합쳐 처리하거나, 한 호출의 취소가 다른 호출에 영향을 주면 안 되며, 종료 뒤 늦은 결과를 내보내면 안 된다.

```text
$codify
동일 키의 동시 조회는 하나의 진행 중 작업을 공유하도록 수정해줘.
호출 하나가 취소돼도 공유 작업과 다른 호출은 유지해야 한다.
서비스 종료는 진행 중 작업의 정리를 기다리고, 기다리던 호출에는 취소를 전달한다.
종료 후 새 요청은 거부하고, 실패 후에는 새 시도를 허용해줘.
취소·종료·늦은 완료 순서를 바꿔 검사하고 시작한 작업을 모두 정리해줘.
```

**확인할 결과:** 작업 소유권, 즉시 관측되는 취소 효과, 정리 완료, 재시도와 늦은 결과 처리. R3 보충 진단에서는 C0의 특정 종료 결함을 C24와 A가 피했다. 이 한 사례로 모든 비동기 구현에서 우위가 있다고 해석하지 않는다.

## 사용5: 중요한 정책이 빠졌거나 이미 결정된 기능

**적합한 상황:** 재고 부족 시 전체 주문을 거절할지 일부만 예약할지처럼 선택에 따라 공개 행동과 데이터가 달라진다. 반대로 이미 정한 정책은 다시 승인받을 필요가 없다.

```text
$codify
재고 예약 기능을 구현해줘.
같은 SKU는 합산하고, 성공한 같은 주문의 재시도는 중복 예약하지 않아야 한다.
재고가 부족한 주문을 어떻게 처리할지는 아직 결정하지 않았다.
결과를 바꾸는 선택은 구현 전에 한 번에 물어보고,
그 선택과 무관한 코드 확인은 계속 진행해줘.
```

정책이 이미 정해졌다면 마지막 두 문장 대신 다음처럼 제공한다.

```text
재고가 하나라도 부족하면 전체 주문을 거절하고 상태를 바꾸지 않는다.
부족 목록은 SKU순으로 반환한다. 이 정책은 결정됐으니 다시 승인받지 말고 구현해줘.
```

**확인할 결과:** 미결정 정책을 임의로 정하지 않음, 기존 답변·승인 재사용, 답변 후 정확한 구현. R4/R5에서는 필요한 질문과 추가 질문 없는 완료를 확인했다. R4가 공개 과제에서 질문을 요구했으므로 숨은 정책 누락을 스스로 발견하는 능력까지 입증하지는 않았다.

## 사용6: 여러 모듈의 구현 인계와 통합

**적합한 상황:** 파서와 처리 모듈처럼 공개 인터페이스와 파일 소유권을 나눌 수 있고, 담당 에이전트도 동시에 진행할 일이 있다.

```text
$codify
CSV 파서와 가져오기 처리·요약 기능을 구현해줘.
공개 계약과 고정 모델을 먼저 확인해줘.
분담이 도움이 되면 작업자는 파서 파일만, 담당 에이전트는 처리·요약 파일을 맡아줘.
작업자에게 접근 가능한 계약과 경로, 파일 소유권, 완료 조건을 전달해줘.
반환된 실제 코드를 검토해 수락·보완 이유를 남기고,
담당 에이전트가 최종 통합 동작과 관련 회귀를 직접 확인해줘.
```

**확인할 결과:** 구체적인 기여, 실제 소스 검토와 반영, 최종 통합 검사, 전체 사용량·시간. 파일 수나 작업자 수 자체는 좋은 결과의 근거가 아니다. 작은 연결된 작업이면 단독 구현이 적절할 수 있다. R6 보충에서 명시적으로 요청한 단일 작업자 인계를 확인했으며, 자발적 분담 판단이나 비용·속도 우위는 미입증이다.

## 사용7: 승인된 계약을 따라 지속적으로 구현

**적합한 상황:** 기능을 여러 단계로 구현하거나 기존 명세의 중요한 결정·승인 상태를 보존해야 한다.

```text
$codify
이미 승인한 기능 계약을 기준으로 다음 미완료 작업을 구현해줘.
시작 경로와 승인된 계약 위치는 다음과 같다: <실제 경로>.
현재 작업의 사용자 흐름과 완료 조건을 먼저 확인하고 구현·검증을 끝내줘.
새로운 중요한 결정이 생기면 영향을 받는 범위와 필요한 질문을 알려줘.
완료 보고에는 요구사항별 근거와 실행하지 못한 필수 검사를 구분해줘.
```

**확인할 결과:** 승인·제안·구현·실행 검증 상태의 구분, 현재 작업 완료와 증거, 계약 변경 시 필요한 상태 갱신. 이 모드는 기존 `specification.md`와 `delivery.md`가 지원한다. 최종 대표 6개 평가가 장기 프로젝트의 전체 계약 수명주기를 보증한 것은 아니다.

## 결과를 읽는 기준

- 확인1: 테스트 개수보다 어떤 요구와 실패 원인을 검사했는지 본다.
- 확인2: 실제 실행한 검사와 계획만 있는 검사를 구분한다.
- 확인3: 작업자 성공 보고와 담당 에이전트의 통합 검증을 구분한다.
- 확인4: 토큰 감소·짧은 응답·깨끗한 리뷰를 코드 품질이나 전체 속도 우위로 대신하지 않는다.

현재 설치본의 기본 요청은 `$codify <코딩 요청>`이다. 단순 설명·번역·한 줄 수정에 추가 계약이나 분담 절차를 붙일 필요는 없다.
