# Codify

Deliver the original requested behavior. Preserve unrelated changes and existing public contracts. Keep a compact acceptance-and-check plan. User instructions and approved contracts control scope and authorization.

## Find the edit and resolve choices

When the request identifies affected files or entry points, start there with applicable repository instructions, contracts, tests, callers and dirty changes. Batch independent targeted reads. Expand discovery only to answer a specific unresolved dependency or behavior question. Stop when the public path, edit boundary, acceptance checks and consequential uncertainties are understood.

Resolve choices from repository evidence and current user instructions first. Ask one focused, bundled question for an unresolved decision that changes public behavior, persisted data, authorization, security, money, destructive effects, compatibility or acceptance. Do not invent that policy or request approval already given. Keep other assumptions narrow, reversible and visible.

For requested specification, slicing, approval or amendment work, read [references/specification.md](references/specification.md) and preserve its approval/amendment gates. For unresolved intent, read [references/intent-interview.md](references/intent-interview.md). A durable slice marked Proposed or review-pending is ineligible for implementation, even when its parent is approved. Preserve amendment resets and required independent review. For verification or status requests, read [references/delivery.md](references/delivery.md) and report or verify within that requested mode. Ordinary authorized code work does not require a new document or approval pause.

## Implement and prove the behavior

Use existing public behavioral checks when they already expose the defect and cover acceptance. Add or change tests for uncovered behavior or risks, not to duplicate the same proof. Establish focused Red when practical, then implement one coherent behavior unit. Missing dependencies, compilation failures and timeouts alone do not establish Red.

For controllable asynchronous work, capture the future and assert required immediate effects before awaiting completion that broken code may never reach. Settle pending test work in failure-safe teardown and bound waits with a justified short timeout.

Select evidence for every applicable trigger:

- Changed observable behavior: focused public behavior checks.
- Shared modules or public contracts: affected caller regressions and required build/static checks.
- Trust boundaries: abuse cases, denial before side effects, validation before writes and safe error output.
- Persistence work: validate before writes and verify preservation/recovery after partial failure, even when the stored format is unchanged. Add compatibility or migration checks when formats change.
- Asynchronous paths: relevant ordering, stale-result, cancellation, failure-recovery, concurrency or stability checks.
- Repository policy: required commands.

A known command is not a coverage argument. Read [references/delivery.md](references/delivery.md) for unresolved coverage/method or repeated slices. Complete the applicable coverage plan and missing related tests before final validation. Confirm intended edits and test insertion in the diff before expensive checks. Run focused checks first, then required affected checks. Repeat only when inputs/environment change or a failure or concrete unresolved risk justifies it. Classify behavior, environment and evidence-collection failures before changing code. Preserve original acceptance criteria when a check is difficult.

## Delegate only useful independent work

Keep one owner of scope, overlapping edits, diagnosis, integration and completion. Delegate only for consequential independent judgment or useful parallel work with independent dependencies and non-overlapping ownership. State the specific question, decision it affects, file boundary, expected evidence and stopping condition. Read [references/orchestration.md](references/orchestration.md) when delegating. Use or explicitly reject returned evidence before adding another worker. Include all workers, failures, waiting and integration in cost/time. Follow the runtime model policy.

## Close from evidence

Inspect the final diff against the original outcome and every applicable criterion. Report delivered behavior, actual checks, remaining gaps and assumptions. Distinguish proposed, approved, implemented and runtime-verified work. Required but unexecuted checks leave completion open.
